### R1 · unstated assumptions · the two MCP write tools hit endpoints that write no audit entry

- **Doc anchor:** §7.1, "A write made through a tool is audited with the key's `api_key_id`." Also §9.3, "With a member key, the item is added and the audit log has a row with the key's `api_key_id`", and §11, "with a member key, its writes appear in the audit log under its key."
- **Claim:** The design assumes that every write endpoint writes an audit entry. The two write tools call `POST .../watchlists/{id}/items` and `DELETE .../items/{item_id}`, and neither handler calls `srv.auditLog`. The §7.1 guarantee, the §9.3 test and the third §11 acceptance criterion cannot hold against the current server. §10 does not list the server change they need, and neither does the §13 delivery list.
- **Evidence:** `grep -n "auditLog" internal/api/watchlists.go` matches lines 256, 307, 515, 559 and 691 only: the tier-limit refusal, watchlist create, update and delete, and `replaceWatchlistItemsHandler` (line 691, and only when `Added > 0 || Removed > 0`). `createWatchlistItemHandler` (lines 573–623) ends with `writeJSON(w, http.StatusCreated, ...)` and has no audit call. `deleteWatchlistItemHandler` (line 763 on) has none either. `auditLog` (`server.go` line 543) would record `api_key_id` from `ctxAPIKeyID` if it were called. The plumbing exists; the two call sites do not.
- **Axes:** objective. Remedy: a choice (add auditing to the two handlers as a listed server dependency, or drop the audit claims).

### R2 · unstated assumptions · struct tags cannot produce the "narrow" input schemas the design promises

- **Doc anchor:** §7.2, "Input schemas are narrow: enumerations are enumerated, numbers have bounds, strings have the server's length limits, IDs have patterns ... and no object accepts properties it does not list. The schemas are generated by the SDK from Go input structs, so the struct tags are their single source."
- **Claim:** The design assumes the SDK's schema inference reads enums, bounds, length limits, patterns and "exactly one of" constraints from struct tags. It does not. The only tag it reads is `jsonschema`, and it uses that tag as the description. Inference by itself yields types, `required` (from the absence of `omitempty`) and `additionalProperties: false`. Every other constraint must be added by code that edits the inferred `*jsonschema.Schema` or replaces `Tool.InputSchema`. The struct tags therefore cannot be the single source. The SDK validates input against whatever schema it is given (`mcp/server.go` line 402, `applySchema`), so a schema built from tags alone accepts out-of-range limits, unknown severities and malformed IDs. Those inputs then reach the API.
- **Evidence:** `jsonschema-go@v0.4.3/jsonschema/infer.go`, lines 79–80: "This function recognizes struct field tags named "jsonschema". A jsonschema tag on a field is used as the description for the corresponding property." Lines 329–336 set `fs.Description = tag` and nothing else. Line 248 sets `AdditionalProperties = falseSchema()`. The file reads no `enum`, `minimum`, `pattern`, `maxLength` or `oneOf` tag. Read in the local module cache, which holds both `go-sdk@v1.8.0` and `jsonschema-go@v0.4.3`.
- **Axes:** objective. Remedy: determinate in kind (post-process the inferred schemas, or write them out), with a choice of where the single source lives.

### R3 · unstated assumptions · the spec-conformance oracle omits query parameters the client sends

- **Doc anchor:** §9.1, "A test checks each against the checked-in `openapi.json` ... A renamed field or a removed parameter fails here." §4.2, "A test (no database) checks every operation the client calls against the checked-in `openapi.json`."
- **Claim:** The design assumes that `openapi.json` documents every parameter the client sends. `GET /cves` reads `cvss_min`, `cvss_max`, `epss_min` and `epss_max` from the raw query string in `Resolve`, and these fields carry no `query:` tag, so they are absent from the spec. These are the parameters behind `--cvss-min`, `--cvss-max`, `--epss-min` and `--epss-max` (§5.2) and behind the MCP inputs `min_cvss` and `min_epss` (§7.2). The conformance test as written either fails on its first run or must exempt these parameters. An exemption gives them no protection against renames, which is the test's purpose.
- **Evidence:** `internal/api/cves.go` lines 262–267: "Not tagged with query: because huma panics on pointer types in query params", followed by `CVSSMin *float64` and the other three. `grep -n "cvss\|epss" openapi.json` returns no parameter named `cvss_min` or `epss_min`. The `/cves` parameter list (around `openapi.json` line 8256) is `q`, `severity`, `date_from`, `date_to`, `cwe_id`, `ecosystem`, `package_name`, `in_cisa_kev`, `exploit_available`, `cursor`, `limit`.
- **Axes:** objective. Remedy: a choice (document the four parameters in the served spec, which is a server change §10 does not list, or carry a documented exception in the test).

### R4 · unstated assumptions · `check --input trivy` assumes the endpoint answers a whole OS package inventory; it answers only Debian and Ubuntu binaries mapped to source

- **Doc anchor:** §6.1, "For a `deb` purl the CLI substitutes the source package ... so the server does the ecosystem mapping and the CLI does not repeat it." §11, "A script on a timer, with only `cvert` and `jq`, can check a list of purls".
- **Claim:** The Trivy path silently assumes three things.
  - **(a) Every OS package in a report is a type the endpoint accepts.** The endpoint refuses `rpm` purls with `unsupported_purl_type`. Every OS package from a RHEL, Alma, Rocky, SUSE or Amazon image therefore comes back `invalid`, and the design does not say so.
  - **(b) Only `deb` needs source-name substitution.** `apk` is accepted and named by `name`, while Alpine advisories are keyed by origin (source) package. Trivy's `SrcName` for apk is the origin, so subpackages such as `libcrypto3` (origin `openssl`) would answer `cannot_evaluate` with `distro_package_not_found`. This should be confirmed against a golden apk report.
  - **(c) The endpoint is sized for a full OS inventory.** The version-check design accepted `distro_package_not_found` for every source package that has no advisories because "few distro items will reach this endpoint". A `--list-all-pkgs` report sends every OS package of an image, so most of a clean Debian image would come back `cannot_evaluate`.

  The design's dependency on the version-check design's assumption is not written down.
- **Evidence:** `internal/api/check.go` line 51, the purl doc: "Types npm, pypi, golang, maven, cargo, gem, nuget, pub, hex, composer, deb (with a distro qualifier) and apk (with a distro qualifier)." `dev/plans/2026-11-08-version-check-endpoint-design.md` §3 table: "`apk` | `Alpine:v<major>.<minor>` from `distro` | `name`" and "anything else, including `rpm` | refused: `unsupported_purl_type`". Its §6 Binary names: "That cost is small, because per-host distro matching stays with Trivy and few distro items will reach this endpoint."
- **Axes:** (a) and (c) objective; (b) objective in mechanism, with the Alpine naming to be confirmed by a golden report. Remedy: a choice (substitute for apk, skip or warn on rpm, or scope `--input trivy` to language packages plus deb).

### R5 · unstated assumptions · the FEED-1 "exact need" omits gap-freedom, and an `after` poller cannot see reopened events

- **Doc anchor:** §10, FEED-1 row: "An ascending order selected by `after`, a `limit` parameter, and a cursor returned on every page that holds items, including the last, so a poller can store it and resume after the last event it saw." §11, "poll alert events with a stored cursor".
- **Claim:** The design assumes that a stored ascending cursor sees every event exactly once. Two properties of `alert_events` break this, and the exact-need row specifies neither.
  - **(a) Late commits are skipped.** `first_fired_at` defaults to `now()`, which is the transaction's start time, and the ID tiebreak is a random UUIDv4. An event whose transaction began before a poll and committed after it sorts behind the stored cursor and is never returned. This is the flaw recorded as NOTIFY-20.
  - **(b) Reopened events are never re-delivered.** `ReopenAlertEvent` reopens an existing row (it sets `last_match_state = true` and `last_fired_at = now()`), and fan-out treats a reopen as a new alert. A poller positioned past that row never sees it again.

  Because §10 is the contract the parallel session builds to, these omissions carry into the server.
- **Evidence:** `migrations/000016_create_alert_runs_events.up.sql` line 48, `first_fired_at TIMESTAMPTZ NOT NULL DEFAULT now()`. `internal/store/queries/alert_rules.sql` lines 81–95 (ReopenAlertEvent). `dev/implementation-pitfalls.md` NOTIFY-20, The Lesson: "A timestamp cursor is safe only if every row is stamped by the same clock that sets the cursor and becomes visible before any later cursor is taken." CLAUDE.md, alert evaluation: fan-out also runs when "a no-op insert was followed by `ReopenAlertEvent` changing a resolved event back to open".
- **Axes:** (a) objective, as a known project pitfall; (b) objective in mechanism, while whether a poller must see reopens is contestable. Remedy: a choice (a commit-ordered sequence column, a rescan overlap with client dedup, or a cursor over `last_fired_at`).

### R6 · unstated assumptions · the retry budget and page sizes assume `Retry-After: 60` reflects availability; with the real bucket, `--all` and large `check` runs fail by default

- **Doc anchor:** §5.5, "The server sends `Retry-After: 60`, so the default allows about one retry." §5.2, "`--all` ... stops with an error above 10,000 items". §11, "replace a watchlist's CVE items from a scanner report".
- **Claim:** The org bucket refills one token per second (60 a minute, burst 10), but the server always answers 429 with `Retry-After: 60`. A client that obeys the header fully gets about 10 requests a minute, not 60. The 2-minute default budget therefore allows about 20 requests per command. Two consequences are not stated:
  - `watchlists items list --all` pages 50 items at a time, so it exits 6 at roughly 1,000 items. Its 10,000-item cap would take 200 requests.
  - `rules list --all` and `watchlists list` page 20 at a time.
  - `check` of about 9,500 purls or more (19 or more batches, plus any 422 splits, plus `whoami` if AUTH-5 puts it under the limiter) exits 6 on a free-tier org. Other keys and the web UI draw on the same bucket, which lowers these thresholds further.

  The design also does not consider waiting less than `Retry-After`, and does not raise the 60-second constant as a server-side problem.
- **Evidence:** `internal/api/middleware_tier.go` lines 63–71: `ratePerSec := rate.Limit(float64(ratePerMin) / 60.0)`, `burst := ratePerMin / 6`, `w.Header().Set("Retry-After", "60")`. `internal/api/watchlists.go` line 717, `const limit = 50` (items); line 356, `const limit = 20` (watchlists); `internal/api/alert_rules.go` line 333, `const limit = 20`.
- **Axes:** objective (arithmetic from the code). Remedy: a choice (raise the default budget, make the server's `Retry-After` reflect the bucket, add a page-size parameter, or document the ceilings).

### R7 · unstated assumptions · 403 does not mean "the key's role is wrong", and `whoami` at startup may not catch the states that make every tool fail

- **Doc anchor:** §5.4, "401 means replace the key, 403 means the key's role is wrong." §7.2, "the key's role decides what it can do." §7.1, "A 401 or 403 there ends the process ... the server does not start in a state where every tool fails."
- **Claim:** The effective role is the lower of the creating user's current membership role and the key's role. A membership that has been deactivated, or a user who is no longer a member, gives 403 on every org route even though the key itself is valid and correctly scoped. So 403 can mean "the person who issued the key was demoted or removed", which is not fixed by changing the key's role. In addition, `/cves` routes check only that the key is valid and its user is enabled, not membership. If AUTH-5 authenticates `whoami` the same way (the design assumes it sits outside the org limiter, "like `/cves`"), then `whoami` succeeds at startup for a deactivated member while every org-scoped tool returns 403. That is exactly the state §7.1 says cannot occur. §10's "exact need" for AUTH-5 does not require `whoami` to apply the membership check.
- **Evidence:** `internal/api/middleware_rbac.go` lines 42–64: `GetOrgMemberRoleAndStatus`, then `if member.DeactivatedAt.Valid { ... 403 }`, then "Cap effective role to the API key's role", then `if effectiveRole < minRole { 403 }`. `internal/api/middleware_auth.go` `tryAPIKeyAuth` checks only `IsUserEnabled`. `internal/api/cves.go` `registerCVERoutes` uses only `requireAuthHuma`.
- **Axes:** the role semantics are objective; whether `whoami` must enforce membership is contestable, because AUTH-5 is unbuilt. Remedy: a choice (state the requirement in §10, and reword the exit-code text).

### R8 · unstated assumptions · `depguard` checks direct imports only, so it does not keep database code out of the binary

- **Doc anchor:** §7.1 item 1, "A `depguard` rule refuses, in the non-test files of `cmd/cvert`, the API client package and the MCP package, any import of `internal/store`, `internal/api`, `internal/config`, `web`, `github.com/jackc/pgx`, and `database/sql`." §3, "No database code and no server configuration in the binary."
- **Claim:** The design treats the `depguard` rule as a transitive guarantee. `depguard` inspects each file's own import statements. Importing any other internal package that itself reaches the store passes the rule. The no-`web/dist` build (item 2) catches only `web`. The design's own §2 names such a package: `internal/alert/dsl`, which is the natural import for the `validate_rule` description.
- **Evidence:** `go list -deps ./internal/alert/dsl` includes `database/sql`, `database/sql/driver` and `github.com/scarson/cvert-ops/internal/store/generated` (run in this worktree). `internal/ecosystem`, which the Trivy path may want for purl handling, is clean. A transitive check would be a test or CI step asserting that `go list -deps ./cmd/cvert` contains none of the denied paths.
- **Axes:** objective (depguard semantics, plus the measured dependency). Remedy: determinate (add a transitive `go list -deps` assertion).

### R9 · unstated assumptions · the check slot is server-wide, unqueued and try-acquire, and the design assumes contention is brief and fair

- **Doc anchor:** §5.5, "**503 with `Retry-After` from `/check`:** the check slot was busy. Wait for `Retry-After` plus up to 500 ms of jitter and retry". §7.5, "Tool calls follow section 5.5 with a budget of 5 seconds ... A busy check slot (`Retry-After: 1`) is retried inside the call."
- **Claim:** `maxConcurrentChecks = 1` applies to the whole process across all orgs, and `acquireCheck` is a non-blocking `select` with no queue. A CLI `check` of thousands of purls sends 500-item batches back to back, each holding the slot for up to 30 seconds. Between batches the slot is free only for one round trip. Every other caller, in any tenant, polls once a second and will almost never land in that gap. An MCP `check_components` call with a 5-second budget fails for the whole length of another org's batch run, and so does a second CLI run. The design assumes slot waits are short and that polling is a fair way to wait for the slot. Neither is stated, and the multi-tenant effect (one org's cron job blocks every org's agents) is not weighed.
- **Evidence:** `internal/api/check.go` lines 25–29 (`maxConcurrentChecks = 1`, `checkTimeout = 30 * time.Second`) and lines 262–268 (`select { case srv.checkSem <- struct{}{}: return true; default: return false }`).
- **Axes:** the mechanism is objective; its severity is contestable (it depends on how many tenants run large checks). Remedy: a choice (client-side pacing between batches, a server queue, or documenting the limitation).

### R10 · unstated assumptions · MCP tool calls queue without bound behind one request at a time, and host timeouts and cancellation are not considered

- **Doc anchor:** §7.5, "An MCP host may send several tool calls at once; the server still sends one API request at a time, and a call waiting for its turn does not spend its retry budget while it waits."
- **Claim:** A `check_components` call can hold the single request lane for 30 seconds per batch. After a timeout it splits once into two halves, which is up to about 90 seconds before any slot-busy waits. Calls queued behind it wait with no bound. MCP hosts apply their own request timeouts, and the design does not say what happens when the host gives up or sends `notifications/cancelled`. It does not say whether a queued call is removed from the queue, or whether an in-flight HTTP request is aborted. The design assumes host patience it does not state.
- **Evidence:** the 30-second check limit and the split-once rule are in §6.2 step 4. The document has no statement on queue bounds, cancellation or the host's timeout.
- **Axes:** contestable (host timeouts vary). Remedy: a choice (bound the queue wait, propagate cancellation, document it).

### R11 · unstated assumptions · `cves search --all` assumes the corpus does not change during the walk

- **Doc anchor:** §5.2, "`--all` follows `next_cursor` until the server returns none, and prints one envelope `{"items": [...]}` holding every item."
- **Claim:** `/cves` pages by keyset on `(date_modified_canonical DESC, cve_id DESC)`. A CVE that the merge pipeline updates during the walk moves ahead of the cursor and is skipped, with no error. A script using `--all --date-from X` as "everything changed since X" can miss records. Feeds ingest continuously, so this happens in normal operation. The output gives no sign that the result may be incomplete.
- **Evidence:** `internal/store/cve.go` `SearchCVEs`: `WHERE (cves.date_modified_canonical, cves.cve_id) < (?, ?)` and `OrderBy("cves.date_modified_canonical DESC, cves.cve_id DESC")`.
- **Axes:** objective in mechanism; contestable in impact. Remedy: a choice (document it, or recommend ascending `date_from` windows with overlap).

### R12 · unstated assumptions · the design assumes a TLS-terminating reverse proxy, and does not consider how proxy responses interact with the 503 split rule

- **Doc anchor:** §5.1, "`http://` is refused unless the host is a loopback address ... No flag overrides this." §6.2 step 4, "On 503 without `Retry-After` (the 30-second limit or a statement timeout), split the batch in two halves once".
- **Claim:**
  - **(a) Every remote deployment needs a reverse proxy.** The server has no TLS listener, so the CLI can reach a server on another host only through a TLS-terminating proxy. The design and `docs/client.md` (§8.3) do not state this precondition.
  - **(b) The split rule misreads proxy errors.** It assumes that every 503 without `Retry-After` on `/check` comes from the server's time limit. A proxy's 503 while the upstream is restarting or unavailable is split once and then reported as `unanswered`, giving exit 9 ("partial result") when the true outcome is a server outage (exit 7).
- **Evidence:** `grep -rn "ListenAndServeTLS\|ServeTLS\|TLS_CERT" cmd internal/config` returns nothing. `internal/api/check.go` `writeCheckFailure`: the server's own timeout 503 carries a fixed detail string ("the version check took too long ..."), which the client could match instead of relying on the absence of a header.
- **Axes:** (a) objective; (b) objective in mechanism, minor in impact. Remedy: (a) determinate (document it); (b) a choice (match the problem detail or type, or have the server mark the timeout 503 with a problem type).

### R13 · unstated assumptions · `go install ...@<version>` assumes tagged releases and build-time version stamping

- **Doc anchor:** §3, "`go install github.com/scarson/cvert-ops/cmd/cvert@<version>` works". §8.2, "Version and commit set by the same ldflags as the server; `cvert --version` prints them". §5.1, "`User-Agent` of `cvert/<version>`".
- **Claim:**
  - **(a) No tags exist.** The repository has no tags, so `@<version>` can only be `@latest` (a pseudo-version of the default branch, `main`) or a commit. That build can differ from the server's commit, the skew §5.6 already warns about.
  - **(b) `go install` does not apply the project's ldflags.** For the install path the design recommends, `--version`, the MCP implementation info and the User-Agent would print whatever the unset variables default to, unless the code falls back to `runtime/debug.ReadBuildInfo`.
- **Evidence:** `git tag --list` in this repository returns nothing. `gh repo view scarson/CVErt-Ops` reports `PUBLIC`, so the proxy can fetch the module. `go.mod` has no `replace` directive, which `go install pkg@version` would reject.
- **Axes:** objective. Remedy: a choice (tag releases, read build info as a fallback).

### R14 · unstated assumptions · deb source substitution says nothing about the binary's `epoch` qualifier

- **Doc anchor:** §6.1, "name from `SrcName` and version from `SrcVersion` (with `SrcEpoch` when set), keeping the purl's `distro` qualifier."
- **Claim:** The design assumes that `distro` is the only qualifier that matters. A Trivy deb purl carries the binary's epoch as an `epoch=` qualifier. The endpoint prepends that qualifier to a version that has no epoch, and refuses a version whose epoch differs from it (`conflicting_version`). Suppose the rebuilt purl keeps the binary's `epoch` and the source epoch differs, or the source has none. Then the item is either refused or compared with the wrong epoch, and a wrong epoch can wrongly clear or condemn the version. The design does not say whether `epoch` is dropped, kept or replaced.
- **Evidence:** version check design §3: "For `deb`, an `epoch` qualifier must be digits, and is prepended to the version when the version has none ... A version that carries a different epoch from the qualifier is refused with `conflicting_version`."
- **Axes:** objective as a gap; the remedy is determinate (drop the binary's `epoch` qualifier and carry the source epoch in the version).

### R15 · unstated assumptions · the exit-6 test assumes 11 requests finish before one token refills

- **Doc anchor:** §9.2, "the 11th request inside the 10-request burst of a free-tier org with `--max-wait 0` (6)."
- **Claim:** The bucket refills one token per second. The test assumes that 10 sequential requests through a real server with a testcontainers database all complete within about 1 second. If they do not, the 11th request succeeds and the test fails intermittently. On this host, the project notes heavy Docker contention. The limiter takes an injectable clock (`newOrgRateLimiter(now, ...)`), and production passes `time.Now`. The design does not say how the test controls time.
- **Evidence:** `internal/api/org_ratelimit.go` `Allow` → `e.limiter.AllowN(rl.now(), 1)`. `internal/api/server.go` line 102, `newOrgRateLimiter(time.Now, evictTTL)`.
- **Axes:** objective in mechanism; contestable in likelihood. Remedy: a choice (a fixed clock in the test server, or exhaust the bucket with a single request of a higher weight).

### R16 · unstated assumptions · "the MCP and CLI tests can share one test binary" conflicts with the package layout

- **Doc anchor:** §9.4, "The MCP and CLI tests can share one test binary to keep that to one container." §8.1 puts the CLI in `cmd/cvert` and the MCP server in `internal/mcpserver`.
- **Claim:** Go builds one test binary per package. With the §8.1 layout, the end-to-end tests are in two packages and start two PostgreSQL containers, unless the tests move to a single dedicated package, which the design does not say. This matters on a host where container load is a recorded problem.
- **Evidence:** §8.1 table, together with CLAUDE.md: "each test binary starts one Postgres container on its first `testutil.NewTestDB` call".
- **Axes:** objective. Remedy: determinate (name one e2e test package, or accept two containers).

### R17 · unstated assumptions · for Trivy input, `index` points at a list the caller never sees

- **Doc anchor:** §6.1, "The CLI sets no item `id`. ... the result's `index` and `component` already identify the item." Also "Identical purls are sent once."
- **Claim:** For `--input trivy`, the items are built by the CLI: deduplicated, with source names substituted. Each `index` refers to a position in that internal list, not to anything in the report. The table column "item index" (§5.3) and the `unanswered` `index` then mean nothing to the caller. The claim holds only for `purls` and `json` input.
- **Evidence:** §6.1 and §6.3 as quoted. The design defines no mapping back to report entries.
- **Axes:** objective. Remedy: a choice (set `id` to a report reference, or document that `component` is the only identifier for Trivy input).
