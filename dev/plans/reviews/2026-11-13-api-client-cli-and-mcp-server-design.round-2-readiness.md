**R1** · downstream readiness (pitfall: testing-pitfalls §7 "Audit trail completeness")
- **Anchor:** §7.1, "A write made through a tool is audited with the key's `api_key_id`." Also §9.3, "the audit log has a row with the key's `api_key_id`", and §11, "its writes appear in the audit log under its key".
- **Claim:** The server writes no audit entry for the two writes the MCP server exposes. The planned test and the acceptance criterion would fail against unchanged server code. The design does not list the server change needed to make them pass.
- **Evidence:** In `internal/api/watchlists.go`, `createWatchlistItemHandler` (lines 573–624) and `deleteWatchlistItemHandler` (lines 763–793) contain no `srv.auditLog` call. `grep -n "auditLog(" internal/api/watchlists.go` returns only lines 256, 307, 515, 559 and 691: tier-limit failure, create watchlist, update, delete watchlist, and replace items. Item add and item remove are not among them. `srv.auditLog` (server.go:543) would attach `api_key_id` if called. The plan author has to choose between adding server-side audit entries, which is new scope on `internal/api` and needs a check of the `audit_log.action` CHECK constraint (testing-pitfalls §16), and dropping the claim.
- **Axes:** objective. Remedy is a choice: add audit to item add and delete, or reword §7.1, §9.3 and §11.

**R2** · downstream readiness
- **Anchor:** §6.1, "For a `deb` purl the CLI substitutes the source package: name from `SrcName` and version from `SrcVersion` (with `SrcEpoch` when set)".
- **Claim:** The version built this way leaves out the Debian revision. Every substituted `deb` item would be checked at the wrong version, and versions below a distro fix like `3.0.11-1~deb12u2` would read as affected or not according to the upstream part only. The planned golden-fixture task confirms field names only, so it would not catch this.
- **Evidence:** Trivy's `pkg/fanal/types/package.go` has separate `SrcVersion`, `SrcRelease` and `SrcEpoch` fields. Its dpkg analyzer (`pkg/fanal/analyzer/pkg/dpkg/dpkg.go`, fetched 2026-11-13) sets `pkg.SrcVersion = v.Version()`, `pkg.SrcEpoch = v.Epoch()` and `pkg.SrcRelease = v.Revision()`. The upstream version and the Debian revision are split, so the full source version is `[SrcEpoch:]SrcVersion[-SrcRelease]`. §6.1 says the fixture task "confirms" the field names, not the composition.
- **Axes:** objective. Remedy is determinate: compose epoch, version and release, and assert the full version string in the golden test.

**R3** · downstream readiness
- **Anchor:** §7.2, "Input schemas are narrow: enumerations are enumerated, numbers have bounds, strings have the server's length limits, IDs have patterns … no object accepts properties it does not list. The schemas are generated by the SDK from Go input structs, so the struct tags are their single source."
- **Claim:** The SDK's schema inference cannot produce enums, bounds, patterns, length limits or "exactly one of" from struct tags. A plan author following the design as written cannot build the narrow schemas, and must invent the mechanism: a hand-built `InputSchema`, post-processing the inferred schema, or `ForOptions.TypeSchemas`. The "single source" claim also no longer holds.
- **Evidence:** `google/jsonschema-go@v0.4.3/jsonschema/infer.go` lines 79–81 say "A jsonschema tag on a field is used as the description for the corresponding property. For future compatibility, descriptions must not start with "WORD="". Lines 329–336 copy the tag into `Description` only, and line 333 rejects `WORD=` prefixes, so `enum=`, `minimum=` and `pattern=` are errors. Inference does set `additionalProperties: false` (line 248). The rest is not expressible. §7.2's `check_components` "each exactly one of `{purl}`, `{ecosystem, name, version}`, `{cpe, version}`" and `add_watchlist_item` "exactly one of `cve_id`, `{ecosystem, package_name}`, `cpe`" need `oneOf`, which inference never emits. The patterns for `get_advisory.id`, which accepts non-CVE advisory IDs per §5.2, and the length limits for `query` and similar inputs are also unstated.
- **Axes:** objective (verified in source). Remedy is a choice of mechanism.

**R4** · downstream readiness
- **Anchor:** §9.1 Spec conformance, "A test checks each against the checked-in `openapi.json` … A renamed field or a removed parameter fails here." §5.2 `cves search` flags `--cvss-min`, `--cvss-max`, `--epss-min`, `--epss-max`. §7.2 `search_advisories` inputs `min_cvss`, `min_epss`.
- **Claim:** The conformance test as specified fails on its first run. Four query parameters the client sends are missing from the spec. The plan author has to choose between fixing the server's spec, which is a change to `internal/api`, and adding an allow-list exception to the test.
- **Evidence:** `internal/api/cves.go` lines 263–268: `CVSSMin`, `CVSSMax`, `EPSSMin` and `EPSSMax` have no `query:` tag ("Not tagged with query: because huma panics on pointer types"). They are read in `resolveOptionalFilters`. Running `python -c "...d['paths']['/cves']['get']['parameters']..."` on `openapi.json` prints `['q', 'severity', 'date_from', 'date_to', 'cwe_id', 'ecosystem', 'package_name', 'in_cisa_kev', 'exploit_available', 'cursor', 'limit']`, with no `cvss_min`, `cvss_max`, `epss_min` or `epss_max`.
- **Axes:** objective. Remedy is a choice: document the parameters in the spec, which is probably right since `schema.d.ts` lacks them too, or except them in the test.

**R5** · downstream readiness
- **Anchor:** §6.2, "4. On 503 without `Retry-After` … split the batch in two halves once and send each. A half that times out again is not split further. 5. An item that alone gets 422 for the candidate limit, or alone times out, is unanswered." Also §5.4 exit codes 6, 7 and 9.
- **Claim:** The failure handling of a multi-batch `check` is not defined well enough to implement. Four gaps:
  - (a) Step 4 stops splitting a half that times out again, but step 5 covers only a single item. Nothing says whether the items of a 250-item half that timed out twice become `unanswered`.
  - (b) It is not said whether 422 splitting and 503 splitting compose. For example, does a half produced by a 503 split still get split recursively on a later 422?
  - (c) A batch that fails with something other than 422 or 503 after earlier batches succeeded: 429 after the budget runs out, 5xx, 401, or a network error. Nothing says whether the command prints the merged partial output and exits 9, or prints nothing and exits 6, 7 or 4.
  - (d) §5.4 gives exit 6 for "the check endpoint stayed busy" and exit 9 for "answered some items and could not answer others". When the busy slot exhausts the budget at batch 3 of 5, both apply, and no precedence is given.
- **Evidence:** The quoted steps, and the exit table, where code 9 says only "could not answer others (section 6.2)".
- **Axes:** objective (ambiguity). Remedy is a choice.

**R6** · downstream readiness
- **Anchor:** §5.2 `events list [--after CURSOR] … [--all]`, and "`--all` follows `next_cursor` until the server returns none, and prints one envelope `{"items": [...]}`". §10 FEED-1, "An ascending order selected by `after` … a cursor returned on every page that holds items, including the last".
- **Claim:** The polling flow that §11 makes an acceptance criterion ("poll alert events with a stored cursor") cannot be planned from the doc. Three gaps:
  - (a) Bootstrap. If FEED-1's ascending order is selected by `after`, a first poll with no stored cursor gets the existing newest-first order and a descending `cursor`. Nothing says how a poller obtains its first ascending cursor, or what `--after` is sent on the first run.
  - (b) `--all` stops when no cursor is returned, but FEED-1 returns a cursor on every page that holds items. For events, `--all` must instead stop on an empty page, and the doc does not say so.
  - (c) The `--all` envelope `{"items": [...]}` drops the cursor, so a poller using `--all` cannot store where to resume.
- **Evidence:** The quoted text. §5.3 also says a list "without `--all` prints the server's … envelope unchanged", which implies the cursor is lost with `--all`.
- **Axes:** (a) is contestable, since it depends on FEED-1's final shape. (b) and (c) are objective. Remedies are choices; for example, carry `next_cursor` in the `--all` envelope for events.

**R7** · downstream readiness
- **Anchor:** §7.4, "Null and empty fields are omitted."
- **Claim:** It is not defined whether `false` counts as "empty". If it does, the MCP results lose distinctions the server makes on purpose. If it does not, `null` versus `false` still collapses to absent versus `false`, which the descriptions must explain. A plan author has to decide this, and either choice changes what an agent can infer.
- **Evidence:** `internal/api/check.go` line 124: `InCISAKEV *bool` "null when the record names no CVE that is held, which means not known, not false". Line 123: `EPSSScore` "null … which means not known". The compact shapes in §7.4 carry `in_cisa_kev`, `epss`, `open`, `partial`, `summary_truncated` and `advisories_truncated`. Omitting a false `partial` or `in_cisa_kev` reads the same as omitting an unknown one.
- **Axes:** objective (ambiguity). Remedy is a choice: never omit booleans, or state which fields are kept.

**R8** · downstream readiness (pitfall: implementation-pitfalls ARCH-28 "External API Client Construction Must Not Make Network Calls")
- **Anchor:** §7.1, "At startup the server calls `whoami`. A 401 or 403 there ends the process with exit code 4 or 5 … the server does not start in a state where every tool fails."
- **Claim:** Startup behavior is specified only for 401 and 403. Nothing says what happens on a connection failure, a TLS error, a 5xx, a 429 (if `whoami` is inside the org limiter; §10 leaves that open), or a redirect: exit, retry, or start and report the error per tool call. ARCH-28's lesson ("the application's ability to start must depend only on local resources … never on external service reachability") points toward not exiting on reachability failures. The design's wording points the other way, and an agent host that starts the MCP server before the API is reachable would get a dead server.
- **Evidence:** The quoted text. ARCH-28 lines 2367–2417.
- **Axes:** The undefined behavior is objective. Whether ARCH-28 applies to a client is contestable. Remedy is a choice.

**R9** · downstream readiness
- **Anchor:** §7.5, "Tool calls follow section 5.5 with a budget of 5 seconds instead of 2 minutes." Also §7.2, where `check_components` is "batched as in section 6".
- **Claim:** It is not said whether the 5-second budget bounds only retry waits or the whole tool call. `check_components` can legitimately run 30 s, then split on 503 into two more 30 s requests (§6.2 step 4), and on 422 recurse about nine levels for 500 items. The §5.1 per-request timeout is 60 s. A plan author must decide whether a split cascade inside a tool call is bounded, and by what. The design also does not say whether queued tool calls (§7.5, "waiting for its turn") have any bound, while one `check_components` call can hold the single request slot for minutes.
- **Evidence:** §5.5 defines the budget as covering waits for `Retry-After` ("wait for `Retry-After` and retry, while the wait fits in the remaining budget"). §6.2 has no budget check on splits.
- **Axes:** objective (ambiguity). Remedy is a choice.

**R10** · downstream readiness
- **Anchor:** §5.2 `watchlists items add … (--cve ID | --package ECO/NAME | --cpe CPE)...`, "prints the items added before it". `watchlists items remove`. §5.3, "A single-resource command prints the server's response body unchanged".
- **Claim:** Several stdout and exit contracts that scripts depend on are unspecified:
  - (a) What `items add` prints on success with N items. N `201` bodies concatenated would break §5.2's "every command's output a single JSON document" rule. An envelope is not specified.
  - (b) What `items remove` prints on success, given that the server answers 204 with no body.
  - (c) Which exit code `--all` uses when it "stops with an error above 10,000 items". Exit 2 is defined as "No request was sent", which is false here. Whether partial items are printed is also unsaid.
  - (d) The exit code for `check` input that is empty after skipping blank and comment lines. The server answers 422 for zero items.
- **Evidence:** The quoted text. The server's `deleteWatchlistItemHandler` writes `http.StatusNoContent` (watchlists.go:792).
- **Axes:** objective. Remedies are small choices.

**R11** · downstream readiness
- **Anchor:** §5.2, `watchlists items replace <watchlist-id> (--file ITEMS.json | --cves FILE|-)`.
- **Claim:** The format of `ITEMS.json` is not given. It could be the server's `{"items":[...]}` body, a bare array, the server item shape with `item_type`, or the CLI's `ECO/NAME` form. For `--cves`, the doc does not say whether IDs are trimmed, upper-cased, de-duplicated, or skip blank and comment lines as `check --input purls` does.
- **Evidence:** §6.1 specifies both of these for `check`'s `json` input ("`{"items": [...]}` or a bare array"). §5.2 specifies neither for `--file`.
- **Axes:** objective. Remedy is a choice.

**R12** · downstream readiness
- **Anchor:** §7.4 `get_advisory`, "affected package ranges …; NVD CPE matches with their range bounds; CNA product entries; up to 20 references … Each list notes how many entries it omitted."
- **Claim:** Only references have a cap. The plan author must invent caps for package ranges, CPE matches and CNA entries, which can be large for kernel or vendor CVEs. Without caps, "notes how many entries it omitted" has nothing to count.
- **Evidence:** The quoted text. `CVEDetail` in `internal/api/cves.go` lines 86–92 returns all of these lists unbounded.
- **Axes:** objective. Remedy is a choice of numbers.

**R13** · downstream readiness
- **Anchor:** §6.3, "`results`: every batch's results, each `index` rewritten to the item's position in the whole input"; "`unanswered`: … `problem` is the server's problem title".
- **Claim:**
  - (a) For `--input purls`, "position in the whole input" can mean the ordinal of the item, after blank and comment lines are skipped, or the line number. For `--input trivy` it can only mean the position in the derived, de-duplicated list, which the user never sees. The plan author must choose, and the output contract depends on the choice.
  - (b) The server's problem `title` is always `http.StatusText(status)`, so `problem` would be "Unprocessable Entity" or "Service Unavailable". The informative text is in `detail`.
- **Evidence:** `internal/api/contract.go` lines 30–40 and 61–72: `Title: http.StatusText(status)`, with the message in `Detail`.
- **Axes:** (a) objective ambiguity, remedy is a choice. (b) objective, remedy is determinate: use `detail`, or the problem `type` plus `detail`.

**R14** · downstream readiness
- **Anchor:** §5.2 command table.
- **Claim:** The paging flags are inconsistent, and a plan author must fill in the gaps. Only `cves search` has `--cursor`. `rules list` and `watchlists items list` have `--all` but no `--cursor`. `watchlists list` has neither, though the server pages it at 20 (`watchlists.go:356`). Without `--all`, a script receives `next_cursor` (§5.3) but cannot pass it back.
- **Evidence:** Server page sizes: watchlists 20, rules 20 (`alert_rules.go:333`), items 50 (`watchlists.go:717`). All three accept `cursor` per `openapi.json`.
- **Axes:** objective. Remedy is determinate: add `--cursor` and `--all` uniformly.

**R15** · downstream readiness
- **Anchor:** §7.1, "Three things keep it that way: 1. A `depguard` rule refuses … any import of `internal/store`, … 2. A CI step builds `./cmd/cvert` in a checkout with no `web/dist`". Also §3, "No database code and no server configuration in the binary."
- **Claim:** Neither check enforces the binary-content guarantee transitively. depguard checks a file's own import list. The no-`web/dist` build catches only `web`. Importing a permitted-looking package such as `internal/alert/dsl` or `internal/ai` links `internal/store/generated` without tripping either check. There is no observable seam, such as a `go list -deps ./cmd/cvert` assertion, that a test could check.
- **Evidence:** `go list -deps ./internal/alert/dsl` lists `github.com/scarson/cvert-ops/internal/store/generated`, and so does `go list -deps ./internal/ai`. §2 already notes this for the DSL package, but the enforcement in §7.1 would not stop it.
- **Axes:** The enforcement gap is objective. Whether it matters is contestable. Remedy is determinate: a deps-list test or CI step.

**R16** · downstream readiness (pitfall: implementation-pitfalls ARCH-13 "Indirect LLM Prompt Injection via CVE Descriptions")
- **Anchor:** §7.3, "**Untrusted text.** Advisory descriptions and references come from external feeds. `get_advisory` and `search_advisories` say so". Also §7.4, "the full description cut at 4,000 characters".
- **Claim:** The design passes feed text, up to 4,000 characters per advisory plus reference URLs, to an agent that can be given a destructive tool (`remove_watchlist_item`). It relies only on a sentence in the tool description. ARCH-13's fix also strips control characters, markdown link syntax and HTML before the text reaches a model, using `internal/ai/sanitize.go`. The design neither applies this nor explains why it should not. Reusing that sanitizer is not straightforward: `internal/ai` transitively links `internal/store/generated` (see R15). A plan author has to decide whether to sanitize and where the code lives.
- **Evidence:** ARCH-13 (implementation-pitfalls lines 2232–2242). §5.3 already replaces control characters in table cells for terminals, but §7.4 does nothing comparable for MCP results.
- **Axes:** contestable. The agent host, not the server, owns the model, and the write tools are gated by a flag and the key's role. Remedy is a choice.

**R17** · downstream readiness
- **Anchor:** §9.4, "The MCP and CLI tests can share one test binary to keep that to one container." §9, "the production handler from `internal/api` … served over loopback".
- **Claim:**
  - (a) A Go test binary is one package. The CLI tests use `run(...)` in `cmd/cvert` and the MCP tests target `internal/mcpserver` (§8.1). Sharing a binary means putting one set in the other's package, and the doc does not say which. Each package that starts a database also needs `TestMain` with `testutil.Run` (project CLAUDE.md).
  - (b) The test server must be built with `api.NewServer(store, cfg, api.ServerDeps{...})`. The doc does not say that `ServerDeps.AlertEvaluator` must be set, or `rules dry-run` returns 503 "dry-run not available" (`alert_rules.go:683–685`). It also does not say that `ServerDeps.AuditWriter`, which is asynchronous, must be set and flushed for any audit assertion (`server.go:543–557`, which is a no-op when nil). The only external construction example, `internal/api/smoke_test.go:66`, passes an empty `ServerDeps{}`.
- **Evidence:** As cited.
- **Axes:** objective. Remedies are determinate but must be written down.

**R18** · downstream readiness
- **Anchor:** §11, "An agent configured with a viewer key and the default flags can answer 'is component X at version V affected by CVE Y, and which version fixes it on the same release line' in at most three tool calls".
- **Claim:** This criterion describes how an agent behaves and gives no way to verify it. No test in §9 checks it, and no manual run, fixture component or expected answer is named. As written, a plan author cannot mark it met or not met. The "three tool calls" also names only two (`check_components`, then `get_advisory`).
- **Evidence:** §9.3 tests tool results, not this question.
- **Axes:** contestable. Remedy is a choice: a scripted tool sequence against `SeedCorpus` with a named CVE and component, or a manual acceptance step.

**R19** · downstream readiness (pitfalls: implementation-pitfalls FEED-20 and NOTIFY-17, response body draining and bounds; testing-pitfalls §8 "Production client configuration exercised in tests")
- **Anchor:** §5.1, "does not follow redirects (a redirect is reported as an error)"; §9.1 Configuration tests.
- **Claim:** Minor. The design does not ask the client to drain response bodies or bound how much it reads. FEED-20 says draining "applies to ALL outbound HTTP responses", and NOTIFY-17 bounds the read with `LimitReader`. Of the production client's policies, the redirect refusal (exit 1) and the absent cookie jar have no test in §9.1 or §9.2. Testing-pitfalls §8 asks that security-relevant client configuration be exercised. The cookie jar matters because `csrfProtect` exempts a request only when it carries no `access_token` cookie (`middleware_csrf.go:30–34`).
- **Evidence:** As cited.
- **Axes:** objective, low severity. Remedy is determinate: add the tests and one sentence.
